# P1.4 — Instruction and storage candidate comparison

Date: 2026-09-19. Baseline revision: `7e29ecd`. The sources described here are
working-tree changes. This is a functional and cycle-count study, not a mapped
CMOS5L cost report: every area column below reads **not measured**, and P5 supplies
those numbers against the sizes recorded here (phase_plan.md P1.4, P5.1).

Nothing in this document decides the ISA. P1.5 chooses a provisional encoding
through a recorded architecture decision; what P1.4 owes it is measurements of two
shapes of the same work and the limits each shape imposes. Section 9 lists what the
measurements recommend and what they leave open.

## 1. What was compared, and how

Two instruction encodings, each stored in two memory-word widths
([`study_encoding.ml`](../f_model/study_encoding.ml)):

| Candidate | Instruction | Memory word | Packing |
| --- | --- | --- | --- |
| `i16/m16` | 16-bit, with extension words | 16-bit | one instruction per word |
| `i16/m32` | 16-bit, with extension words | 32-bit | two instructions per word, earlier in the less significant half |
| `i32/m32` | fixed 32-bit | 32-bit | one instruction per word |
| `i32/m16` | fixed 32-bit | 16-bit | one instruction across two words, less significant first |

Both encodings carry the same operation set
([`study_isa.ml`](../f_model/study_isa.ml)), drawn from construction-plan.md
section 4's family table: eight 16-bit registers, two-address arithmetic, three
flags, masked pin writes in immediate and register forms, an input-snapshot read,
the timing and queue operations [`Operation.t`](../f_model/operation.ml) already
defines, and nine descriptor-field writes plus an issue for the transfer engine.
Programs are written once and assembled by every candidate, so the differences
below are differences of encoding and not of instruction selection.

Every number was run rather than computed
([`test_encoding.ml`](../test/f_model/test_encoding.ml)). A program is assembled into
real words, loaded into a [`Program_store`](../f_model/program_store.ml) through the
1RW contract port, and executed by [`Study_core`](../f_model/study_core.ml), which
issues its operations into [`Machine`](../f_model/machine.ml) through the same
ready/valid port the P1.1 tests use. The SPI and I2C traces are answered by the
independent peers in [`firmware_spi.ml`](../f_model/firmware_spi.ml) and
[`firmware_i2c.ml`](../f_model/firmware_i2c.ml), which follow the wire and nothing
else.

### The reference microarchitecture

The cycle counts depend on a core, and the one used is deliberately the simplest
thing that respects the memory contract:

1. Fetch is **not** overlapped with execution. Each memory word an instruction
   needs costs one edge, on which the read is driven into the port; its data is
   consumed at the next edge, which is the contract's latency of one.
2. **One memory word is buffered.** A second instruction slot in the same word is
   therefore free — that is the whole of what packing buys — and a taken branch
   throws the buffer away.
3. Execution is **one edge per instruction**, on which any operation is offered to
   the machine. A stalling operation adds its own edges.

Every candidate runs on this same core. An overlapped fetch would lower every
absolute number here without changing their ratios; `fetch` and `execute` are
reported separately so a reader can bound that without rerunning anything. Loading
the image is host work (P3.1a) and is not counted.

## 2. Instruction packing, extension words, and byte order

The 16-bit format keeps five bits of opcode and eleven of payload. Twenty-seven
opcodes are defined, leaving five reserved. One rule governs every immediate: each
instruction with one carries an `x` bit, and `x` means *the inline field is zero and
the next word is the full sixteen-bit value*. An extension is always exactly one
word, and no per-opcode table of "which immediates may extend" is needed.

| Instruction | Inline immediate at 16 bits | Extends when |
| --- | --- | --- |
| `Ldi`, `Cmp_imm` | 7 bits | value > 127 |
| `Alu_imm` | 4 bits | value > 15 |
| `Config` | 6 bits | value > 63 |
| `Wait_cycles_imm`, `Start_periodic` | 10 bits | value > 1023 |
| `Wait_level` timeout | 5 bits | timeout > 31 |
| `Wait_edge` timeout | 4 bits | timeout > 15 |
| `Write_pins_imm` | — | always: eight bits of mask and eight of value do not fit |

Of the 105-instruction corpus that exercises every form at its inline boundary, 29
need a second word at 16 bits and none do at 32. The realistic triggers are ordinary:
a pin mask above `0x7f`, a bit period above 1023 cycles (9600 baud at 50 MHz is 5208),
an I2C stretch timeout of 64, and the transmitted word of a UART descriptor.

The 32-bit format keeps six bits of opcode and gives every immediate sixteen bits
inline. Twenty-seven of sixty-four opcodes are defined. Its spare room is real and
was deliberately **not** spent: `Alu` leaves nine bits free, which is where a
three-address form would go, and every immediate instruction leaves at least four.
Both encodings are two-address here so that one program text measures both;
section 9 leaves the three-address question to P1.5.

**Byte order** is little-endian and is a property of the transport, not of the
format: the loader assembles complete memory words before issuing writes
(construction-plan.md section 4), so byte order describes how a host byte stream
becomes words and never how the core reads them. In a 32-bit word holding two
16-bit instructions the earlier instruction occupies the less significant half, so
both conventions agree that earlier is lower. One three-instruction program, as
words and as the bytes a host would send:

| Candidate | Memory words | Transport bytes |
| --- | --- | --- |
| `i16/m16` | `0980 1234 783c 000a 5ffb` | `80 09 34 12 3c 78 0a 00 fb 5f` |
| `i16/m32` | `12340980 000a783c 00005ffb` | `80 09 34 12 3c 78 0a 00 fb 5f 00 00` |
| `i32/m32` | `04801234 3c1e1400 2ffffffd` | `34 12 80 04 00 14 1e 3c fd ff ff 2f` |
| `i32/m16` | `1234 0480 1400 3c1e fffd 2fff` | `34 12 80 04 00 14 1e 3c fd ff ff 2f` |

The odd half-word left by an odd number of 16-bit instructions in a 32-bit memory
word is written with `Halt`, so running into the padding stops the core. An
*unwritten* word is a different thing and faults; see section 6.

Program bits, 16-bit instructions against 32-bit, at equal memory width: **−26%**
for the unrolled frame, **−46%** for the bit loop, **−50%** for the SPI exchange,
**−45%** for the descriptor program, **−37%** for the I2C transaction. Extension
words never cancel the halved instruction width; the worst case here, the I2C
transaction, still spends 22 of them and still ends 37% smaller.

Against construction-plan.md section 4's sweep points, the I2C transaction is the
only example that presses on the store: it fits 128 words under every candidate
except `i32/m16`, which needs 170 and is refused at that depth. A 256×16 store is
4,096 bits; the same 256 instructions in a 32-bit word are 8,192.

## 4. Cycle counts

Same programs, same countdown immediates, against the same peers. `stall` is the
firmware's own countdowns and level waits and is identical under every candidate;
`fetch` and `execute` are what the encoding costs and are the columns to compare.
Every edge is one of the three kinds, which the test asserts.

`i16/m16` costs `i32/m32` nothing where no extension words are executed (SPI: 325
against 325; the bit loop: 173 against 172, its one extension outside the loop) and
costs 9% to 14% where they are (I2C: +9%, unrolled UART: +14%). `i16/m32` is the
fastest candidate on every example: packing removes 15% to 26% of `i16/m16`'s cycles
for the same program bits, and it is 8% to 23% ahead of the next fastest candidate.
`i32/m16` is the slowest on every example, 13% to 43% behind the next slowest, and
is also the largest in memory words.

### The cost of one instruction, and of each branch path

Cycles attributable to one instruction, measured as the difference between a probe
and a baseline that executes everything but it, so that a taken branch is charged
for the buffered word it discarded:

| | `i16/m16` | `i16/m32` | `i32/m32` | `i32/m16` |
| --- | --- | --- | --- | --- |
| One-word instruction | 2 | 1 | 2 | 3 |
| Instruction with an extension word | 3 | 2 | 2 | 3 |
| `Jump` | 2 | 2 | 2 | 3 |
| `Branch`, taken | 2 | 2 | 2 | 3 |
| `Branch`, not taken | 2 | 1 | 2 | 3 |
| `Dbnz`, taken | 2 | 2 | 2 | 3 |
| `Dbnz`, not taken | 2 | 1 | 2 | 3 |

Under the two unpacked candidates every path costs the same, because every
instruction fetches its own word whether it was reached by falling through or by
branching. Only the packed candidate distinguishes them, and it does so in the
useful direction: a not-taken branch whose successor shares its memory word is free
to fetch, while a taken branch pays for the discarded buffer. `Dbnz` is one
instruction on every candidate; the fused form is why a bit loop closes in one
instruction rather than two, and its saving is the same for both encodings.

## 5. What the bit-banged wire timing actually was

A fetch happens between two pin writes, so the bit period is the countdown plus the
encoding's own overhead. With the same program and the same countdown of three:

| Program | `i16/m16` | `i16/m32` | `i32/m32` | `i32/m16` |
| --- | --- | --- | --- | --- |
| Unrolled | 8, uniform | 6 and 7, **not uniform** | 7, uniform | 9, uniform |
| Unrolled, slot-aligned | 10, uniform | 8, uniform | 9, uniform | 12, uniform |
| Bit loop | 15, uniform | 13, uniform | 15, uniform | 21, uniform |

Shortest achievable bit period, the same programs with the shortest countdown an
instruction can carry:

| Program | `i16/m16` | `i16/m32` | `i32/m32` | `i32/m16` |
| --- | --- | --- | --- | --- |
| Unrolled | 6 | 4, not uniform | 5 | 7 |
| Unrolled, slot-aligned | 8 | 6 | 7 | 10 |
| Bit loop | 13 | 11 | 13 | 19 |

At a **nominal** 50 MHz — nominal because no timing closure has been run — the bit
loop's 13 cycles is 3.8 Mbit/s and the unrolled frame's 6 is 8.3 Mbit/s. The
transfer engine's own schedule is two cycles a bit at `half_period = 1`, and it
occupies the core for none of them.

**Packing costs uniform bit timing, and the fix is measurable.** The unrolled
frame's body is three instruction slots under a 16-bit encoding — a pin write of two
words and a countdown of one. Packed two slots to a memory word, consecutive bits
therefore start in opposite halves and fetch a different number of words, and the
bit period alternates between 6 and 7. An independent bit-centre receiver reads that
frame as `0x26` instead of `0xa6`; every other row in both tables decodes correctly.
Padding each bit to an even number of slots restores uniformity, and the "slot-
aligned" rows are that experiment: it costs one word and one edge per bit — 45
instruction words against 34, and 90 cycles against 73 — and gives `i16/m32` a
uniform 8-cycle bit at the same countdown. A loop needs no padding, because every
iteration re-enters at the same slot: the bit loop is uniform under all four
candidates.

## 6. Invalid instructions

Both decoders accept a word only if its opcode is defined, every bit its layout does
not use is zero, and every enumerated field names something. The consequences:

| Condition | Result |
| --- | --- |
| Reserved opcode | `Reserved_opcode`; the core halts at that slot with the pins as they were |
| A bit set outside the layout | `Reserved_bits_set` |
| A field naming nothing (`alu_op` 5–7, descriptor field 9–15, zero shift amount, zero delay, a timeout flag disagreeing with its value) | `Field_out_of_range` |
| A word the store never had written | `Unspecified`, before decoding: the contract does not define it and P1.1 forbids accepting it as an instruction |
| Branch displacement out of the field | refused by the assembler, not at run time |
| Image larger than the store | refused by the assembler |

An invalid instruction halts the core and leaves the pins driving whatever they were
driving. That is P1.1's rule for a bad fetch — a program error is not an abort, and
whether to abort, reset or inspect is the host's decision — applied to decoded words
as well as unspecified ones. Recovery is P3.

**How much of each word space is an instruction at all.** Exhaustively at 16 bits,
and over a million words of a fixed-seed uniform sample at 32:

| | Words that decode | Of |
| --- | --- | --- |
| 16-bit instruction word | 15,518 | 65,536 (23.7%) |
| 32-bit instruction word | 17,925 | 1,000,000 sampled (1.79%) |

A randomly corrupted or misaddressed word is executed as though it were an
instruction about one time in four by the 16-bit decoder and about one time in
fifty-six by the 32-bit one: the miss rate is thirteen times lower, because the wider
format has room to leave unused. This is the clearest advantage the fixed 32-bit
encoding has, and it is an error-detection property rather than a correctness one:
neither format can be relied on to catch corruption, and neither has a parity or ECC
scheme.

**An extension word is not self-identifying.** It is sixteen bits of payload with no
tag, so a word that is an extension when reached in sequence is an ordinary
instruction when reached by a branch. The assembler places labels only on
instructions, so a correct program cannot do it; a corrupted program counter can,
and some extension words spell something legal:

| Instruction | Extension word | Decoded as an instruction |
| --- | --- | --- |
| `Ldi r0, 0x2000` | `2000` | `Alu_imm Add r0, 0` — legal, executes |
| `Ldi r0, 1000` | `03e8` | `Reserved_bits_set` — faults |
| `Write_pins_imm mask=1 value=0` | `0000` | `Halt` — legal, stops the core |

The 32-bit candidate has no such word. Removing the hazard from the 16-bit format
costs the tag bit that made it worth measuring, so it is recorded rather than
engineered away; section 9 leaves it to P1.5.

## 7. Register and flag semantics

Identical across both encodings, because one program text had to assemble under
both:

- **Eight 16-bit registers.** Three bits of register field is what makes eight the
  interesting number: a fourth costs more than a 16-bit instruction can spare.
- **Two-address arithmetic.** `rd` is both a source and the destination; a program
  needing its source preserved pays a `Mov`. The 32-bit format has room for a
  three-address form and does not use it here.
- **Three flags** — zero, carry, negative. Carry is the carry out of an addition,
  the borrow out of a subtraction, and the bit shifted out of a shift; the logical
  operations clear it. `Ldi`, `Mov`, `Read_pins` and `Read_status` leave all three
  alone, so a value can be fetched between a comparison and the branch that uses it.
  `Dbnz` leaves them alone for the same reason: a loop counter is bookkeeping, and
  overwriting a comparison with it would cost the instruction the fused form saves.
- **Branch reach**, in instruction slots, measured from the slot after the branch:

  | | 16-bit | 32-bit |
  | --- | --- | --- |
  | `Jump` | ±1024 | ±33,554,432 |
  | `Branch`, `Dbnz` | ±128 | ±32,768 |
  | `Branch_pin` | ±64 | ±32,768 |

  At 16 bits a `Jump` reaches anywhere in a 256-slot store from anywhere in it, and a
  conditional branch reaches half of it — comfortably more than the examples need,
  whose longest loop body is 22 slots, but not an arbitrary target, which is what the
  jump is for. The shorter reach therefore costs nothing at the sizes under study and
  would matter for a larger store. A displacement that does not fit is refused by the
  assembler rather than rewritten into a jump island, because the reach of a branch is
  one of the things being compared.
- **No call and no return**, following construction-plan.md section 4's flow family.
  The I2C transaction pays for that twice: its eight-bit write loop and acknowledge
  slot are 31 instructions and appear once for the address byte and once for the
  payload, so 31 of its 85 instructions exist only because the body could not be
  called. A third byte would cost 31 more. This is the largest single structural cost
  in the study and it is identical under both encodings.
- **No data memory.** The program store is a single 1RW port already shared with
  fetch, so a load or store would need an arbitration contract that does not exist.
  Registers and the two byte queues are the only data.

## 8. The instruction stream against the transfer engine

P1.3 recorded that a UART frame is 22 operations bit-banged or one
`Configure_transfer`, and said that pair of numbers is what P1.4 needs. With fetch
and decode included:

| Way of sending one 8N1 frame | Program bits (`i16/m16`) | Cycles | Cycles the core is occupied |
| --- | --- | --- | --- |
| Unrolled bit-bang | 544 | 90 | all 90 |
| Bit loop | 240 | 173 | all 173 |
| Descriptor, first frame | 192 | 23 | 23, then the engine runs alone |
| Descriptor, each later frame | +48 | +5 | 5, then the engine runs alone |

The descriptor rows stop at acceptance: the machine validates and latches the
descriptor, and executing a transfer is P2.5, so the eighty cycles the engine then
occupies are P1.3's measurement of [`shift_engine.ml`](../f_model/shift_engine.ml) and
not this program's. The later-frame row is the measured difference between a one-byte
and a two-byte program: every descriptor field but the transmitted word still holds,
so a second frame is one `Config` and one `Issue_transfer` — 48 more bits of program
and 5 more cycles under `i16/m16`, 64 bits and 4 cycles under `i32/m32`.

Sending one frame through the engine is a third of the unrolled program's bits and a
quarter of its cycles, and every frame after the first is a fifth of the bit loop's
bits and a thirty-fifth of its cycles — and the core is free for all eighty cycles
the engine then spends on the wire. The instruction stream's own floor, five to seven
cycles a bit and six for the recommended candidate, is the same argument stated the
other way round. Neither result depends on which encoding is chosen.

## 9. What the measurements say, and what they leave open

For P1.5's architecture decision, on this evidence:

1. **Sixteen-bit instructions with extension words.** They cost 26% to 50% fewer
   program bits at equal memory width and cost nothing in cycles except where an
   extension is actually executed, where they cost 9% to 14%. Program storage is
   the dominant state in a design this small — construction-plan.md section 4's own
   figure is 4,352 bits before registers and metadata — and the cycles the extension
   words cost land in firmware's countdowns, which firmware can shorten.
2. **Drop `i32/m16`.** It is the largest and the slowest on every example. A 16-bit
   memory word with 32-bit instructions has no case.
3. **`i16/m32` is the fastest candidate and the most delicate.** It halves fetch
   cycles for the same instruction words - only the padding half-word of an odd
   program costs anything - and it makes bit-banged timing depend on which half of a
   memory word an instruction lands in. If P5's physical evidence favours a 32-bit
   memory word, the packing is worth taking, with the rule that a bit-banged region
   must have an even number of instruction slots between pin writes — measured at one
   word and one edge per bit — or must be a loop, which re-enters at a fixed slot and
   needs no padding.
4. **Spend some of the 32-bit format's spare room, or do not pay for it.** Nine free
   bits in `Alu` are a three-address form that was not measured here. If P1.5 wants
   32-bit instructions, that form should be measured first, because it is the only
   thing that would close the program-size gap.

Open, and deliberately not decided here:

- **A call and return instruction.** 31 of the I2C transaction's 85 instructions are
  the second copy of one inlined byte loop. Either flow instruction pair, or a pointer-driven byte loop,
  would pay for itself immediately; both need a return-address register or a stack,
  which needs data memory or a dedicated register, which is a decision this study did
  not have to make.
- **Whether extension words should be taggable.** Recorded in section 6; costs a bit.
- **Physical area.** Not measured. P5 maps these sizes against the CMOS5L flow and
  the memory-macro question, and section 3's table is the input to it.

## 10. Limitations

- **One microarchitecture.** The cycle counts are for the non-overlapped reference
  core of section 1. Overlapping fetch with execution would reduce every absolute
  number; the fetch and execute columns are reported separately so a reader can bound
  that. The ratios between candidates come from fetch counts and are not affected.
- **One lowering.** The programs are one author's instruction selection. A different
  selection would move the absolute numbers; the same program text was assembled by
  every candidate, so the comparison does not depend on it.
- **No engine execution.** P2.5 has not built the transfer engine into the machine,
  so the descriptor programs stop at acceptance and the engine's wire time is quoted
  from P1.3.
- **No area, no timing closure.** The 50 MHz in section 5 is nominal and no synthesis
  or routing has been run against these structures.
- **The 32-bit decodable-word fraction is sampled**, not exhaustive: a million
  uniform words with a fixed seed. The 16-bit figure is exhaustive.
- **Both encodings are two-address**, so the 32-bit format is measured without the
  three-address form its spare bits would allow.
