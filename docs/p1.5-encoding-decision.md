# P1.5 — Provisional encoding decision, and the shared specification

Date: 2026-09-19. Baseline revision: `64a80d8`. The sources described here are
working-tree changes.

This is the recorded architecture decision phase_plan.md P1.5 asks for. It chooses a
provisional encoding on P1.4's evidence, settles the three questions that study left open,
and says where the specification lives so that the assembler and P3.2's RTL decoder read
one description of it.

**Provisional means provisional.** construction-plan.md section 10 keeps the ISA encoding
open until decoder area is measured, and P5 supplies that. What this document fixes is the
instruction format, the instruction set and the assembler's contract, so that P2 and P3
can be built against something. Physical area remains unmeasured, and section 8 lists what
would reopen the decision.

## 1. The decision in one table

| Question | Decision | On what evidence |
| --- | --- | --- |
| Instruction width | Fixed **16 bits**, with one-word extensions | P1.4 §3: 26% to 50% fewer program bits at equal memory width |
| Memory word | A **separate, deferred** choice. Default 16-bit, one instruction per word; the packed 32-bit layout is implemented and selected by the caller | P1.4 §5 and §9.3: packing is 15% to 26% faster and breaks uniform bit timing |
| Addressing | **Two-address** arithmetic | Three-address needs a 32-bit instruction, which costs 26% to 50% more program bits |
| Call and return | **Added**: `Call` writes a link register, `Jump_reg` returns | §4 below: 30% fewer instructions on the I2C transaction for 0.9% more cycles |
| Extension words | **Untagged**, as measured | §5 below: the tag costs a bit and buys no guarantee |
| Invalid instruction | **Halts** at the slot, pins hold | P1.1's rule for a bad fetch, applied to decoded words |
| Register file | **Eight 16-bit** registers, three flags | construction-plan.md section 4's starting point, measured in P1.4 |
| Specification | One library, `isa/`, below both `lib/` and `f_model/` | §6 below |

Dropped: fixed 32-bit instructions in either memory width, and 16-bit instructions in a
32-bit word *as a fixed choice*. P1.4 §9.2 found `i32/m16` largest and slowest on every
example; `i32/m32` costs 26% to 50% more program bits and its one real advantage,
error detection, is discussed in §5.

## 2. Instruction width: sixteen bits with extension words

P1.4 assembled the same UART, SPI and I2C programs under four candidates and ran them on
one reference core. At equal memory width the 16-bit encoding cost **−26%** (unrolled UART
frame), **−46%** (bit loop), **−50%** (SPI exchange), **−45%** (descriptor program) and
**−37%** (I2C transaction) of the program bits, and cost nothing in cycles except where an
extension word is actually executed, where it cost 9% to 14%.

Program storage is the dominant state in a design this small — construction-plan.md
section 4's own figure is 4,352 bits before registers and metadata — and the cycles an
extension word costs land in firmware's countdowns, which firmware can shorten. That is
the whole argument, and it is P1.4 §9.1's.

**The extension rule, unchanged from the measured candidate.** Every instruction with an
immediate carries an `x` bit, and `x` means *the inline field is zero and the next word is
the full sixteen-bit value*. An extension is always exactly one word, so a decoder needs
no per-opcode table of which immediates may extend. `Write_pins_imm` is the one
instruction whose extension is not optional: eight bits of mask and eight of value do not
fit beside an opcode in sixteen bits.

**The encoder is canonical**: it never spends an extension word on a value that fits
inline, so a program's size is a function of its values alone and every instruction round
trips through the decoder to itself. Of the 111-instruction boundary corpus in
[`test_isa.ml`](../test/f_model/test_isa.ml), 29 need a second word, and the triggers are
ordinary: a pin mask above `0x7f`, a bit period above 1023 cycles (9600 baud at 50 MHz is
5208), an I2C stretch timeout of 64, and any descriptor field above its inline limit.

## 3. Memory word: still two layouts, and why that is not a dodge

construction-plan.md section 4 requires instruction width and physical memory-word width
to be recorded as separate choices, and P1.4 measured them separately. The instruction is
now sixteen bits. The store's word is not decided here, because the evidence that would
decide it does not exist yet: P1.4 §9.3 found the packed layout the fastest candidate on
every example *and* the only one whose bit-banged timing depends on which half of a memory
word an instruction lands in, and the tie-breaker is the physical cost of a 16-bit store
against a 32-bit one, which is P5.1's measurement.

So [`Assembler.Memory`](../isa/assembler.ml) carries both and the default is `word16`.
Both are exercised by every test below. Measured, on the same programs:

| Program | `m16` words / cycles | `m32` words / cycles | Cycles saved |
| --- | --- | --- | --- |
| UART TX, unrolled | 34 / 90 | 17 / 73 | 19% |
| UART TX, unrolled and slot-aligned | 45 / 112 | 23 / 90 | 20% |
| UART TX, bit loop | 15 / 173 | 8 / 148 | 14% |
| SPI mode 0 | 29 / 325 | 15 / 262 | 19% |

And what packing costs, from the same runs, with an independent bit-centre receiver
reading the line:

| Program | `m16` bit period | `m32` bit period | `m32` received |
| --- | --- | --- | --- |
| UART TX, unrolled | 8, uniform | 6, **not uniform** | `0x26`, not `0xa6` |
| UART TX, unrolled and slot-aligned | 10, uniform | 8, uniform | `0xa6` |
| UART TX, bit loop | 15, uniform | 13, uniform | `0xa6` |

**The rule that comes with packing**, if P5 selects it: a bit-banged region must have an
even number of instruction slots between pin writes, or must be a loop, which re-enters at
a fixed slot and needs no padding. The slot-aligned rows are that padding, and it costs
one word and one edge per bit. This is recorded here rather than enforced by the assembler
because it is a property of a firmware region, not of a program, and no way to mark a
region exists yet.

Both layouts hold a whole number of instructions in a memory word, so a memory read always
reaches a whole instruction slot. That is the property the dropped `i32/m16` candidate
lacked and is why nothing in the assembler splits an instruction across words any more.

## 4. Call and return: added, and what it was measured to be worth

P1.4 §9 left this open and phase_plan.md gave it to P1.5. The cost of not having it was
measured: 31 of the I2C transaction's 85 instructions were a second inlined copy of one
eight-bit byte loop, and a third byte would have cost 31 more.

**What was added.** `Call { link; target }` writes the slot address of the following
instruction into a named register and branches; `Jump_reg { rs }` jumps to the absolute
slot address in a register. There is no stack and no dedicated link register: either would
need data memory or a ninth register, and neither exists. The return address lives in one
of the eight, the callee's contract says which, and a nested call saves it with an
ordinary `Mov` first. `Jump_reg` is absolute where every other flow instruction is
relative — which is what makes a returned-to address meaningful — and it doubles as the
computed jump a dispatch table needs.

**What it is worth.** The same I2C transaction, same target, same acknowledges, written
both ways in [`example_programs.ml`](../f_model/example_programs.ml) with a byte-writer body
that is identical in both:

| | Inlined | Called | Change |
| --- | --- | --- | --- |
| Instructions | 87 | 61 | −30% |
| Memory words (`m16`) | 109 | 77 | −29% |
| Memory bits | 1,744 | 1,232 | −29% |
| Cycles | 908 | 916 | +0.9% |
| Target received | `0x84 0xa5` | `0x84 0xa5` | — |

Eight cycles is exactly the two extra instructions each call site pays, twice. A third
byte would cost three instructions instead of thirty-one.

The two programs are 87 and 61 instructions where P1.4's was 85, because both variants
here move the acknowledge out of a shared register with a `Mov` so that the byte-writer
body is literally the same list of instructions in both. That is what makes the row above
a measurement of the call rather than of two different programs.

**Cost in the encoding.** Two opcodes, taking the defined count from 27 to 29 of 32, and
`Call`'s displacement is eight bits rather than `Jump`'s eleven because the link
register's three bits come out of the same payload. A callee further than ±128 slots is
reached by loading its address and using `Jump_reg`, which loses the return address the
call would have written; at a 256-slot store that is an unusual program, and a longer
reach would have cost a register field the two-address form has no room to give up.

## 5. What was deliberately not changed

**Extension words stay untagged.** An extension word is sixteen bits of payload with no
tag, so a word that is an extension when reached in sequence is an ordinary instruction
when reached by a branch. The assembler places labels only on instructions, so a correct
program cannot do it; a corrupted program counter can, and some extension words spell
something legal:

| Instruction | Extension word | Decoded as an instruction |
| --- | --- | --- |
| `Ldi r0, 0x2000` | `2000` | `Alu_imm Add r0, 0` — legal, executes |
| `Ldi r0, 1000` | `03e8` | `Reserved_bits_set` — faults |
| `Write_pins_imm mask=1 value=0` | `0000` | `Halt` — legal, stops the core |

Tagging costs one bit of every extension word's payload, which is the bit that makes a
16-bit immediate fit at all. It would not make the format safe against a corrupted program
counter — a mistargeted branch can land on an ordinary instruction just as easily — so it
would buy a partial guarantee at the price of the property the format was chosen for.
Recorded, not engineered away.

**Error detection is the fixed-width format's advantage and it was given up knowingly.**
17,532 of the 65,536 16-bit words decode (26.8%); P1.4 sampled the 32-bit format at 1.79%.
A randomly corrupted or misaddressed word is executed as though it were an instruction
about one time in four here, against one in fifty-six there. Neither format can be relied
on to catch corruption and neither has parity or ECC, so this is a difference in how
loudly a broken program fails, not in whether it can. If that is later judged
unacceptable, the answer is a check over the loaded image (P3.1a's readback already reads
every word back) rather than a wider instruction.

**Two-address arithmetic.** `rd` is both a source and the destination; a program needing
its source preserved pays a `Mov`. The three-address form P1.4 left unmeasured is only
available in a 32-bit instruction, and choosing the 16-bit format decides it.

**No load or store.** The program store is a single 1RW port already shared with fetch, so
a data access needs an arbitration contract that does not exist (construction-plan.md
section 4). Registers and the two byte queues remain the only data.

**An invalid instruction halts.** A reserved opcode, a reserved bit set, a field naming
nothing, and a word the store leaves unspecified all end the run at the slot that produced
them, with the pins left driving whatever they were driving. That is P1.1's rule — a
program error is not an abort, and whether to abort, reset or inspect is the host's
decision. Recovery is P3.

**One strictness change from the measured candidate.** This decoder refuses a zero delay,
a zero period and a zero timeout; P1.4's 16-bit decoder accepted them, although its
encoder could never produce one. Across all 55,296 words of the 27 shared opcodes the two
decoders disagree on exactly those 42 words and decode every other word to the same
instruction, which is the test that says the encoding chosen here is the one that was
measured.

## 6. One specification, and where it lives

construction-plan.md section 4: "Keep the instruction specification shared by assembler and
decoder, while the reference execution model stays independent of the Hardcaml
implementation." Those two requirements pull in opposite directions in this repository's
layout, because `lib/` is the installed library and `f_model/` is not, and an installed
library cannot depend on a private one.

So the specification is its own library, `isa/` → `hardcaml_protemu.isa`, below both:

| Module | What it owns |
| --- | --- |
| [`kinds.ml`](../isa/kinds.ml) | The direction-neutral enumerations an instruction field names. Moved down from `f_model/` for that reason |
| [`pins.ml`](../isa/pins.ml), [`event_kind.ml`](../isa/event_kind.ml) | The pin bank's shape and the status word's bit order — both programmer-visible, both previously declared inside the model |
| [`instruction.ml`](../isa/instruction.ml) | The instruction set and per-instruction structural validation |
| [`descriptor.ml`](../isa/descriptor.ml) | The nine descriptor fields, the control word's bits, and how a field value names a pin or a pacing source |
| [`encoding.ml`](../isa/encoding.ml) | Opcodes, field layout, encode, decode |
| [`program.ml`](../isa/program.ml), [`assembler.ml`](../isa/assembler.ml) | Labels, program validation, layout, images |

It holds no execution and no circuit, and it does not depend on Hardcaml. Execution is
[`control_core.ml`](../f_model/control_core.ml) in the model, which has no Hardcaml
dependency either and never will; P3.2's RTL core is the other implementation, and the two
share `Encoding` — the contract both must meet — and nothing else, so a disagreement
between them stays evidence rather than one mistake seen twice.

**The layout is data, not prose.** `Encoding.Layout` declares each instruction's fields
once; `encode` and `decode` use those declarations, and `Encoding.forms` publishes the
same records so that a decoder can be built from them rather than transcribed from a
table. A field's position exists in exactly one place in this repository. The table below
is printed by a test from `Encoding.forms`, so this document cannot drift from the encoder.

```
opcode mnemonic        payload (bits 10..0)
     0 halt            -
     1 ldi             rd:10..8 x:7 imm:6..0
     2 mov             rd:10..8 rs:7..5
     3 alu             op:10..8 rd:7..5 rs:4..2
     4 alu_imm         op:10..8 rd:7..5 x:4 imm:3..0
     5 cmp             ra:10..8 rb:7..5
     6 cmp_imm         ra:10..8 x:7 imm:6..0
     7 shift           dir:10 rd:9..7 amount:6..3
     8 read_pins       rd:10..8
     9 read_status     rd:10..8
    10 ack_status      mask:5..0
    11 jump            disp:10..0
    12 branch          cond:10..8 disp:7..0
    13 branch_pin      pin:10..8 level:7 disp:6..0
    14 dbnz            rd:10..8 disp:7..0
    15 write_pins_imm  mode:10 mask:9..2 value:extension word
    16 write_pins_reg  mode:10 mask_reg:9..7 value_reg:6..4
    17 wait_cycles_imm x:10 imm:9..0
    18 wait_cycles_reg rd:10..8
    19 wait_level      pin:10..8 level:7 t:6 x:5 imm:4..0
    20 wait_edge       pin:10..8 edge:7..6 t:5 x:4 imm:3..0
    21 start_periodic  x:10 imm:9..0
    22 stop_periodic   -
    23 config          field:10..7 x:6 imm:5..0
    24 issue_transfer  -
    25 fifo_push       fifo:10 blocking:9 rs:8..6
    26 fifo_pop        fifo:10 blocking:9 rd:8..6
    27 call            link:10..8 disp:7..0
    28 jump_reg        rs:10..8
```

29 of 32 opcodes are defined; 29, 30 and 31 are reserved and decode to nothing. Every
payload bit a layout does not use must be zero. An enumerated field must name something:
`op` 5–7, `cond` 6–7, a descriptor field 9–15, a zero shift amount, a zero delay or
period, and a timeout flag disagreeing with its value are all refused.

**The room that is left**, per instruction, in spare payload bits: `read_pins`,
`read_status`, `wait_cycles_reg` and `jump_reg` have eight each; `fifo_push` and
`fifo_pop` six; `mov`, `cmp` and `ack_status` five; `write_pins_reg` four; `shift` three;
`alu` and `write_pins_imm` two; and `halt`, `stop_periodic` and `issue_transfer` have all
eleven. The flow instructions, every immediate form and `config` have none — they spent
theirs on reach and on inline values, which is where P1.4 said the pressure was.

## 7. Branch reach, register and flag semantics

Unchanged from what P1.4 measured, except for the call pair.

- **Eight 16-bit registers.** Three bits of register field is what makes eight the
  interesting number: a fourth costs more than a 16-bit instruction can spare.
- **Three flags** — zero, carry, negative. Carry is the carry out of an addition, the
  borrow out of a subtraction, and the bit shifted out of a shift; the logical operations
  clear it. `Ldi`, `Mov`, `Read_pins`, `Read_status` and `Call` leave all three alone, so a
  value can be fetched, or a subroutine called, between a comparison and the branch that
  uses it. `Dbnz` leaves them alone for the same reason.
- **Reach**, in instruction slots, from the slot after the instruction:

  | Instruction | Reach |
  | --- | --- |
  | `Jump` | ±1024 |
  | `Branch`, `Dbnz`, `Call` | ±128 |
  | `Branch_pin` | ±64 |
  | `Jump_reg` | absolute, anywhere in the store |

  A `Jump` reaches anywhere in a 256-slot store from anywhere in it. A displacement that
  does not fit is refused by the assembler, by the label the author wrote, rather than
  rewritten into a jump island.

## 8. The assembler's contract

[`Assembler.assemble`](../isa/assembler.ml) takes a program, a store depth and a memory
layout, and returns the entries, the label map, the image and its size, or one reason it
could not. Everything it refuses, with the reason it gives:

| Condition | Reason |
| --- | --- |
| No instructions | `Empty` |
| The same label twice | `Duplicate_label` |
| A branch to a label that does not exist | `Undefined_label` |
| A register or pin the hardware does not have | `Register_out_of_range`, `Pin_out_of_range` |
| An immediate, delay or shift amount out of range, zero included | `Immediate_out_of_range` |
| A target the instruction's displacement field cannot reach | `Displacement_out_of_range`, naming the label |
| A last instruction execution can continue past | `Runs_off_the_end` |
| An image larger than the store | `Program_too_large` |

`Runs_off_the_end` is new in P1.5 and is worth naming: the word after an image was never
written, so fetching it faults (P1.1 forbids accepting an unwritten word as an
instruction). A program ending in a conditional branch would fault the first time the
branch was not taken, and the assembler says so while the author can still act on it. The
last instruction must be `Halt`, `Jump` or `Jump_reg`.

Byte order is little-endian and is a property of the transport: the loader assembles
complete memory words before issuing writes, so byte order describes how a host byte
stream becomes words and never how the core reads them. In a 32-bit word holding two
instructions the earlier one occupies the less significant half, so both conventions agree
that earlier is lower. One three-instruction program, assembled both ways:

| Layout | Memory words | Transport bytes |
| --- | --- | --- |
| `m16` | `0980 1234 783c 000a 5ffb` | `80 09 34 12 3c 78 0a 00 fb 5f` |
| `m32` | `12340980 000a783c 00005ffb` | `80 09 34 12 3c 78 0a 00 fb 5f 00 00` |

The odd half-word left by an odd number of instructions in a packed image is written with
`Halt`, so running into the padding stops the core. An *unwritten* word is a different
thing and faults.

## 9. What would reopen this decision

- **Decoder and store area (P5.1).** If a 16-bit store is not cheaper than a 32-bit one at
  these depths, the packed layout becomes the default and §3's even-slot rule becomes a
  firmware constraint. If the decoder for a variable-length format costs more than the
  program bits it saves, the whole choice is back open; P1.4 §3's size table is the input
  to that comparison.
- **A program that does not fit.** The I2C transaction is 77 memory words called, of 256.
  Nothing measured so far presses on the store.
- **A real need for nested calls.** The link register makes nesting the firmware's
  problem. If several levels of call turn out to be ordinary, a stack needs data memory,
  which needs the arbitration contract §5 says does not exist.
- **Core timing changes.** The cycle counts here belong to the reference core: fetch not
  overlapped with execution, one buffered memory word, one edge per instruction.
  The subsequent P1.6 decision adopts this as the cycle-exact core contract; see
  [verification.md](verification.md). Overlapped fetch would require an explicit
  architecture revision and renewed model, firmware-timing, and protocol evidence.
  Fetch and execute edges remain separately reported measurements.

## 10. Limitations

- **No area, no timing closure.** Nothing physical has been measured against these
  structures. Every bit period in §3 is in cycles, not in time.
- **No engine execution.** P2.5 has not built the transfer engine into the machine, so the
  descriptor program stops at acceptance and the engine's wire time is quoted from P1.3.
- **One lowering.** The programs are one author's instruction selection. The same program
  text is assembled by both memory layouts, so the comparison between them does not depend
  on it; the comparison against P1.4's other candidates carries that caveat from P1.4.
- **The 42-word strictness difference** in §5 is the only respect in which the committed
  encoding is not bit-for-bit the candidate P1.4 measured, and it is asserted by a test
  rather than argued.

## 11. Reproduction

```sh
./scripts/with-switch.sh dune build
./scripts/with-switch.sh dune runtest test/f_model
./scripts/with-switch.sh dune build @isa/lint @f_model/lint @test/f_model/lint
```

Every number in sections 2 through 8 is transcribed from an expect-test output in
[`test_isa.ml`](../test/f_model/test_isa.ml), which is where to look when one of them needs
checking; only the prose and the percentages computed from those numbers are written by
hand. `dune build @fmt` reports pre-existing differences in `f_model/fifo.ml` and
`f_model/shift_engine.ml` that are unrelated to this work; the files added here are
formatted.
