# P3.1a program-store consumer implementation record

Date: 2026-09-20. Baseline revision: `fbe0a98`. The P3.1a sources and this record are
uncommitted working-tree changes. This is behavioral consumer evidence, not P3.1b/P0.7
backend adoption, mapped memory cost, or instruction execution evidence.

## Implemented boundary

[`Protocol_core`](../lib/protocol_core.ml) remains plain Hardcaml and instantiates no RAM.
It drives one external 1RW port with one shared eight-bit physical word address, enable,
write enable, sixteen-bit whole-word write data, and sixteen-bit latency-one read data.
The fixed P3.1a configuration is 256x16 and directly consumes P1.5's default `m16` image:
one instruction slot per memory word, word-addressed, with little-endian byte assembly left
to the future transport. Host and fetch request addresses and image lengths are nine bits,
so 256 and larger addresses are rejected before the physical address is narrowed.

The core exposes distinct request/decision pairs for load-start, sequential writes,
readback, load-complete, RUN, and fetch. `engines_idle_i` is a real integration input.
Host program access and RUN require `halted_o && engines_idle_i`; running host offers are
explicitly rejected without changing the fetch port. P3.2 receives an explicit interface:

- accepted `run_valid_i` changes ownership from host to execution;
- `fetch_valid_i` plus a bounded word address issues a read when `fetch_accepted_o` is high;
- `fetch_response_valid_o` marks the associated word exactly one edge later;
- absence of a request stalls with the memory disabled, and only one fetch is outstanding;
- an invalid fetch issues no read, latches `fetch_fault_o`, and halts;
- `execution_halt_i` cancels an outstanding fetch response and returns ownership to host.

P3.2 still owns the PC, instruction-slot extraction, decoder, register/flag state, branches,
extension words, instruction faults, and boundary stop semantics. P3.1a does not invent a
temporary instruction or execute returned data.

## Verified loading decision

The contract is recorded in
[`construction-plan.md`](construction-plan.md#program-load-access-and-fetch-contract).
The smallest mechanism that proves complete coverage without a 256-bit validity map is:

1. Declare a nonzero length no greater than 256. An accepted start immediately invalidates
   the old executable image.
2. Accept each write only at the next zero-based address below that length. Missing,
   duplicate, reordered, and truncated writes cannot advance completion.
3. After all writes, read every word back in the same order. Each verification request
   carries the host's expected complete word; hardware associates it with the latency-one
   response and compares all sixteen bits. A mismatch is sticky until a new load-start.
4. Accept load-complete only after every declared word matched, no response is outstanding,
   and no mismatch occurred. Only then can RUN be accepted.

The future loader supplies length and expected words after assembling complete transport
words. Hardware checks write coverage, read coverage, comparison, bounds, and sequencing;
there is no unchecked completion pulse. A shorter replacement cannot reach the old tail.
Reset clears all validity/session/response ownership while preserving RAM contents. Disable
halts and cancels a partial session or pending response but preserves a completed image.

## Verification evidence

[`f_model/program_access.ml`](../f_model/program_access.ml) independently predicts control
from scheduled requests and externally supplied RAM data. It has no Hardcaml dependency and
does not consume DUT acceptance or validity. The local store in
[`protocol_core_testbench.ml`](../test/core/protocol_core/protocol_core_testbench.ml)
implements latency-one reads, disabled-output hold, whole-word writes, no initialization,
and three deterministic choices for unspecified post-write/unwritten output: zero,
all-ones, and address-derived data.

Ten directed tests cover RUN after reset; successful load/verify/RUN; partial, missing,
duplicate, reordered, premature-complete, mismatching, interrupted, and replacement loads;
short-image tail exclusion; zero, depth-sized, and oversized lengths; halted-idle and
engine-busy access; live requests during fetch; ordinary readback; exact response latency;
held-output validity; zero-valued valid instructions; legal final and illegal fetch
addresses; and outstanding-response cancellation across reset, disable, execution halt,
and reload. The generated test runs 240 fresh-state scenarios at seed `20260920`, maximum
size 32, across all request classes, reset/disable, engine-idle changes, and all poison
policies. A mismatch reports edge and observation as the first mismatch, full scenario,
source/dependency/tool identity, artifact, and this rerun command:

```sh
PROTEMU_SEED=20260920 PROTEMU_TRIALS=240 PROTEMU_SIZE=32 dune runtest test/core/protocol_core --force
```

[`generate_core.ml`](../bin/generate_core.ml) emits the consumer alone. `@rtl` runs
Verilator lint and generic Yosys synthesis on that output. This proves elaboration and HDL
tool acceptance, not behavioral equivalence of an ASIC memory backend or mapped physical
quality.

## Completion and handoff

P3.1a is complete. Parent P3.1 and P3.1b remain open.

P3.1b/P0.7 must instantiate the context-registered
`hardcaml_asic.Single_port_ram` at the project top, connect this exact port, rerun these
consumer checks against the selected behavioral/flop implementation and emitted RTL, and
record resource identity, shape, selection, manifest, and mapped cost. It must not move
validity or bounds into the RAM backend.

P3.2 consumes the RUN/fetch/response/halt boundary above and implements the real P1.5/P1.6
non-overlapped fetch/decode/execute schedule. It must retain response validity rather than
infer validity from data and must explicitly revise this record if selecting packed `m32`.
P3.3 later supplies real engine-idle state and execution return/interrupt behavior.
P3.1a alone does not unblock P2.6b: after both P3.2 and P3.3 provide the executable
event-to-core-to-pin path, P2.6b remains the immediate return slice recorded in the phase
plan.

Remaining blockers are exactly those later slices: no context-registered memory, decoder,
instruction execution, engine integration, host transport, mapped cost, or physical timing
is claimed here.
