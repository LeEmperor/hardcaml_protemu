# P3.2 minimal control-execution implementation record

Date: 2026-09-20. The initial P3.2 implementation landed in `61384c3` on baseline
`8d3ada1`; the subsequent collision-priority fixes and this record's updates are uncommitted
working-tree changes. This is functional control-core and emitted-RTL evidence, not P3.3
mechanism integration, mapped physical cost, or protocol acceptance evidence.

## Implemented boundary

[`Executable_core`](../lib/legacy/executable_core.ml) composes P3.1a's external-store consumer
with [`Control_execution`](../lib/emulator_core/control_execution.ml), while leaving the latency-one
program RAM outside the block. An accepted RUN clears the PC, all eight registers, flags,
descriptor fields, retained instruction state, counters, and prior halt/fault status. The
loaded image remains P3.1a state. Reset clears both halves; disable cancels execution while
preserving a completed image. Normal halt and execution faults preserve committed
architectural state for inspection.

The implementation keeps the selected `m16` layout and the P1.6 non-overlapped schedule.
An ordinary instruction has one accepted fetch edge and one execute edge. An extended
instruction has two accepted fetch edges and one execute edge; the due base-word completion
and extension request may turn over on the same edge. The execution client never infers
validity from memory data. P3.1a still owns image validity, physical and loaded-image bounds,
port arbitration, and the fetch-bounds fault.

[`Instruction_decoder`](../lib/emulator_core/instruction_decoder.ml) is combinational and derives opcode
values, field positions, spare masks, and extension shape from `Encoding.forms` and
`Encoding.Layout`. It rejects reserved opcodes/bits, invalid enum fields, malformed inline
or extension forms, zero delays/periods/timeouts where prohibited, and out-of-range pin
write extensions. The procedural `Encoding.decode` received the same missing
`Write_pins_imm` range check, so both decoders reject extension values above `0xff`.

The core executes these instructions locally:

- `Halt`, `Ldi`, `Mov`, `Alu`, `Alu_imm`, `Cmp`, `Cmp_imm`, and `Shift`;
- `Jump`, `Branch`, `Dbnz`, `Call`, and `Jump_reg`;
- `Config`, which updates one field of the retained transfer descriptor.

All other legal P1.5 instructions are represented by one typed P3.3-facing request. The
kind, three operands, timeout-enable bit, and complete descriptor remain stable until the
request is accepted or refused. Acceptance may coincide with completion. After acceptance,
the core does not reissue the command and stalls fetch until completion. A successful
completion commits its result; refusal, completion fault, protocol violation, or unsolicited
completion terminates execution at a non-retiring instruction boundary.

Control-flow targets are calculated at seventeen-bit width before P3.1a's nine-bit request
interface. Negative or otherwise unrepresentable targets are execution faults rather than
wrapped addresses. A representable target outside the verified image is instead P3.1a's
fetch-bounds fault. Base-word, extension, target, mechanism, and unsolicited-completion
faults retain the instruction slot and relevant address/reason. `instruction_boundary_o`
marks retirement, normal halt, and terminating faults; `retired_o` distinguishes successful
retirement. PC, register/flag/descriptor state, phase, and fetch/execute/stall/instruction/
extension/total counters are observable.

STOP, ABORT, single-step, actual pin/timer/event/transfer/FIFO responders, engine-idle
production, and system-boundary pin behavior remain P3.3.

## Verification evidence

The block-owned suite under
[`test/core/control_execution/`](../test/core/control_execution) contains 25 inline test
cases. Its evidence is split by responsibility:

- `instruction_decoder_tests.ml` compares legality and extension classification for every
  one of the 65,536 base words with `Encoding.decode`, then checks extension-presence,
  extension-range, and extended-immediate boundaries. Directed execution checks field
  interpretation; exhaustive field-value equivalence is not claimed.
- `control_execution_model_tests.ml` compares RTL retirement state with the independent
  [`f_model/control_core.ml`](../f_model/control_core.ml) trace across all local instruction
  classes, every ALU operation, every branch condition taken and untaken, DBNZ counts
  zero/one/two, calls, returns, computed jumps, flags, and descriptor writes.
- `control_execution_property_tests.ml` compares 96 deterministic assembled programs at
  seed `20260920`, size 24, and records an executable rerun command.
- `control_execution_mechanism_tests.ml` gives every delegated command kind immediate
  success coverage, then uses representative commands for delayed acceptance/completion,
  stable requests without reissue, result commits, refusal, completion fault, unsolicited
  completion, local-execution collisions, and reset/disable cancellation before acceptance.
- `control_execution_fault_tests.ml` covers reserved opcodes, spare bits, invalid enum and
  extension values, truncated extensions, negative and oversized targets, fallthrough past
  the image, fresh RUN, simultaneous halt/RUN priority, descriptor reset state, disable
  cancellation, live host traffic, and the first/final image slots.

The representative directed image has words
`0880 1234 3080 1234 6001 0a63 0902 71ff 0000`. It executes nine fetch cycles and seven
execute cycles, including two extensions and the final Halt, for sixteen program cycles.

[`generate_core.ml`](../bin/generate_core.ml) now has separate `access` and `executable`
modes. `@rtl` emits the executable composition, runs Verilator lint and generic Yosys
synthesis, and executes [`p3_control_tb.v`](../tinytapeout/test/p3_control_tb.v) against an
independent latency-one Verilog memory model. The testbench loads, verifies, runs, and checks
the representative program and prints:

```text
P3.2 emitted RTL PASS: 9 fetch + 7 execute = 16 cycles
```

This emitted-RTL tier establishes HDL behavior for that program and generic synthesis tool
acceptance. It is not CMOS5L mapping, place-and-route, gate-level, or physical timing
evidence.

## Completion and handoff

P3.2 is complete. P3.3 has since connected this retained mechanism request/completion
boundary to the P2 blocks, supplied real engine-idle state, and implemented boundary STOP,
prompt ABORT, and single-step. It consumes `instruction_boundary_o` rather than inventing a
second instruction-boundary definition.

P3.2 by itself does not claim that delegated instructions perform physical work. The
[P3.3 record](p3.3-implementation.md) owns that evidence and the completed phase-swept
`wait_start_then_drive` measurement.
