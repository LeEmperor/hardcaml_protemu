# P3.4 host API, simulator backend, and CLI guide

Date: 2026-09-20. This record covers the transport-independent host API, the first backend
over the actual P3.3 integrated Cyclesim design, and a stateful CLI workflow. P3.5 has since
fixed the serial framing and hardware loader contract. This record still does not claim a
P3.6 physical-device backend, hardware trace storage, P4 protocol acceptance, mapped cost,
physical timing, or the parent P3 exit gate.

## Implemented software boundary

[`host/host_api.ml`](../host/host_api.ml) is a plain OCaml API below command parsing and
without Hardcaml types. Its `Device` signature covers discovery, safe complete-image load,
ordinary readback and comparison, loaded-image state, RUN/STOP/ABORT/step, status and
architectural inspection, pin claims, host TX/RX queues, explicit cycle advancement,
bounded waits, and trace enable/retrieve/clear. The same types are the handoff for later
physical backends.

Discovery currently reports:

| Field | Simulator value |
| --- | --- |
| API / protocol | `1.0` / `1.0` |
| ISA | `protemu-p1.5`, version 1 |
| Backend | `integrated-core-cyclesim` |
| Program memory | 256 words x 16 bits; memory-word addresses |
| Image | `protemu-image-sexp`, version 1, `m16`, complete words, little-endian transport byte order |
| Pins | Eight; portable configuration is software claim/release |
| Queues | Eight-byte host TX into DUT RX; eight-byte host RX from DUT TX |
| Engines | One transfer lane plus timing/blocking-operation status |
| Trace | Simulator-side, rising-edge-cycle timestamps, configured bounded capacity |

The centralized constants are in `Host_api.Constants`; the CLI does not carry copies.
Structured errors distinguish unsupported/invalid operations, API/ISA/image mismatches,
hardware refusals, accepted-operation timeouts, partial queue transfers, verification
mismatch, hardware fault, parse failure, and I/O failure. CLI error codes are stable short
atoms such as `incompatible_api`, `incompatible_isa`, `active_execution`, `would_block`,
`no_verified_image`, `image_bounds`, `pin_conflict`, `terminal_halt`, `timeout`, and
`transfer_timeout`. A hardware rejection is never converted to success or retried. The
simulator advertises an explicit capability list rather than
`Capability.all`; simulator cycle control, pad stimulus, and simulator-side trace remain
identifiable simulator facilities.

The P3.4 review cleanup completes the first API 1.0 definition before any P3.5 transport or
external physical backend exists, so the version remains 1.0. The reviewed draft's unused
`Load_not_active`, `Invalid_load_sequence`, `Pending_readback`, and `Control_priority`
refusal constructors were removed rather than supported by invented paths; `Image_bounds`
was added for an authoritative completed-image limit. `Hardware_rejected` remains the
fallback only where hardware exposes no stronger cause. Source users of the pre-cleanup
draft must recompile and update exhaustive matches. After this boundary is released, an
incompatible operation/type/error change requires an API-major bump; a backward-compatible
operation or capability addition requires a minor bump. Image format, ISA, CLI envelope,
abstract operation protocol, and the future physical register/wire protocol are separate
version domains and change only with their own contracts.

## Image and program access

An accepted image file is one S-expression with metadata and a list of complete memory
words. [`examples/p3.4-echo.pimg`](../examples/p3.4-echo.pimg) is the smallest example:

```text
((format protemu-image-sexp) (format_version 1) (api_major 1)
 (isa_id protemu-p1.5) (isa_version 1) (layout m16) (word_bits 16)
 (address_unit Memory_word) (byte_order Little_endian)
 (words (54272 51200 0)))
```

`words` are unsigned 16-bit complete words, from address zero, with length 1 through 256.
Raw byte files and `m32` are not accepted. Therefore a partial trailing transport word is
not representable in this format; the P3.5 loader assembles and validates complete
little-endian words before calling this API. Parsing and all metadata/bounds checks happen before
load-start where possible.

`load_image` then drives the real P3.1a sequence: load-start, ordered writes, ordered
hardware readback with each expected word, and load-complete. It succeeds only after
hardware accepts completion. An accepted start invalidates the old image, so a later write,
readback, comparison, or completion failure leaves no executable image. `verify_image`
performs ordinary hardware readback of an already completed image and compares it on the
host. Program requests offered while execution owns memory, or while a background engine
is active after the core halted, are reported as `Active_execution` or `Engines_active` and
do not disturb fetch or RAM state. Status and queues are independent of this restriction.

`read_program` has explicit all-or-error semantics. For a nonempty request it validates the
whole physical range, halted/engine-idle access state, verified-image presence, and completed
image length before reading. `No_verified_image` and `Image_bounds` therefore consume no
cycles and return no partial words. Once that validation succeeds, the state is stable for
the non-destructive read sequence. If hardware nevertheless refuses mid-range, `Read_failed`
contains the original address/count, failing address, completed count, and prior words.
`verify_image` reports `No_verified_image` only when validity is false; a valid image of a
different length returns `Incompatible_image` with requested length as `required` and loaded
length as `actual`, while equal-length data differences return `Verification_mismatch`.

## Simulator session and time

[`host/simulator_backend.ml`](../host/simulator_backend.ml) owns exactly one flattened
[`Integrated_core`](../lib/integrated_core.ml), one 256x16 latency-one external RAM model,
and its clock. It neither calls the functional model nor writes DUT RAM/register/execution
state directly. A new session applies one reset edge internally and exposes cycle zero with
invalid image metadata, empty FIFOs, zero external pads/occupancy, idle mechanisms, and an
empty enabled trace. Reset RAM contents remain unspecified, as required by the memory
contract.

For each advancing operation the backend performs this order:

1. Apply persistent external pads/occupancy and the host offer.
2. Settle combinational logic and sample acceptance plus the external RAM request.
3. Advance one rising edge.
4. Apply the accepted RAM read/write to the contract store and drive held read data.
5. Re-settle after updating latency-one RAM read data, sample registered/combinational
   outputs at that boundary, and append trace observations.

An accepted program read takes an offer edge and one response edge. A complete `N`-word
load takes `1 + N + 2N + 1` edges. RUN returns when accepted and does not hide execution
time. STOP and step accept once, then wait only up to the caller's budget. A timeout says
whether hardware already accepted the operation; it never resets or aborts implicitly.
Background timers, blocking FIFO operations, transfers, and STOP progress on every edge
advanced by any host operation or explicit `advance`/wait.

Discovery, compatibility checks, loaded state, status/register/engine/event/fault/pin
inspection, trace retrieval/clear, and simulator pad changes do not advance time. A pad
change is persistent and is applied before the next request and rising edge. Pin claims,
control offers, successful queue bytes, and program operations do advance time. Queue
budgets bound waiting edges; accepted bytes each use one edge. Budget zero is nonblocking:
a blocked transfer reports `Would_block` without advancing time. Result records retain
requested/transferred counts and received bytes.

The RAM contract guarantees exactly one response edge after an accepted read. Absence of
that response is `Backend_invariant` (or the corresponding `Read_failed` cause for a range),
not an ordinary safely retryable `Timeout`. P3.5 fixes serial response correlation by tag and
command; consuming that contract through a physical backend remains P3.6 work. The post-RAM
settle also makes a full FIFO's readiness include a same-edge
core pop. A blocked zero-budget transfer still advances no edge, while a simultaneous pop
and host push transfers exactly once.

Portable transfer calls return partial progress in `Ok Transfer.t`. The CLI's exact-transfer
wrapper converts non-complete results to `Transfer_incomplete` while retaining all counts
and received bytes. `Timed_out` maps to `transfer_timeout`, distinct from control-operation
`timeout`; retry starts after the reported transferred prefix. The total handler retains a
generic `transfer_incomplete` code for a decoded or externally constructed impossible
`Transfer_incomplete { outcome = Complete; ... }`, but the wrapper never creates it.

## Trace contract

Trace records have monotonic sequence numbers and rising-edge-cycle timestamps. At one
timestamp their ordering is host operation, instruction boundary, mechanism event, engine
completion, committed pin value/output-enable transition, then newly visible fault. Only
those advertised observations are recorded. In particular this is simulator observation,
not hardware-resident trace memory.

Capacity is fixed when a simulator session is created. On overflow the oldest record is
dropped; `overflowed` is sticky and `lost_records` is cumulative until clear. Retrieval is
a non-destructive snapshot after an optional sequence cursor and returns the oldest retained
sequence plus next cursor. Clear removes retained records and clears overflow/loss but does
not rewind the sequence counter. Disable suppresses new records without stalling execution.
Retrieval, enable/disable, and clear consume no simulated cycles. A new session starts empty
at sequence zero. Sequence and loss counters are nonnegative OCaml `int` values. Exceeding
`Int.max_value` is outside the supported lifetime of one simulator session; no wraparound
contract is advertised.

ABORT's accepted edge is also its documented prompt completion boundary. The backend sets
`completed` only after observing the post-edge halted state, idle engines, zero software and
engine claims, and zero output enables. It does not add asynchronous polling. Host pin
configuration is claim/release only; direct host pin driving is intentionally absent.

Execution faults are asynchronous program outcomes, not failed host control offers. They
halt execution and are reported through `Status.fault` and ordered trace records; a later
step is refused as `Execution_faulted`. Program memory is accessible once halted and engines
are idle. Recovery is explicit ABORT for prompt mechanism/ownership cleanup as needed,
followed by reload or fresh RUN; neither wait nor inspection silently clears fault state.
`Hardware_fault` remains available to backends for a host operation that cannot return a
meaningful status, but the integrated simulator does not misclassify an inspectable program
fault as such.

## CLI usage

`protemu sim info` creates a fresh session and emits discovery. Stateful work uses one
`sim script` process; separate shell invocations intentionally do not pretend to share a
device. Every executed script command emits one compact versioned S-expression. Unexpected
errors stop the script with exit status 2. `expect-error CODE ...` asserts a negative case
and continues.

Run the checked acceptance workflow:

```sh
./scripts/p3.4-cli-workflow.sh
```

Its underlying copy-pastable commands are:

```sh
mkdir -p _build/p3.4-cli
./scripts/with-switch.sh dune exec protemu -- sim write-echo-image \
  -output _build/p3.4-cli/p3.4-echo.pimg
cmp examples/p3.4-echo.pimg _build/p3.4-cli/p3.4-echo.pimg
./scripts/with-switch.sh dune exec protemu -- sim script \
  examples/p3.4-workflow.sim -trace-capacity 8
```

`sim write-echo-image` uses the shared assembler to generate the three instructions
`Fifo_pop Rx`, `Fifo_push Tx`, `Halt`. The script discovers and checks compatibility,
rejects an incompatible image before mutation, loads through P3.1a, reads and compares all
three words, and verifies the completed image. It then runs with the core blocked on the
real RX FIFO, confirms live program access refusal, observes an accepted STOP timeout,
injects `0xa5`, and stops at that instruction boundary with register zero equal to `0xa5`.
One step pushes that byte through the real TX FIFO and host RX receives it; another step
reaches Halt. It then demonstrates fresh RUN, live refusal, ABORT, eight-byte fill/ninth-byte
`Would_block`, rerun/reception, final idle/normal-halt status, and released pins. With trace
capacity eight the post-review measured run retains eight records, reports 38 dropped
records, then proves clear resets overflow and retained contents without advancing measured
cycle 67. These whole-workflow values are evidence from this implementation, not portable
API timing guarantees; focused tests pin normative per-operation timing and exact ring
accounting.

The acceptance script also runs a focused exact-transfer workflow whose checked output
contains `transfer_timeout`, requested count 2, transferred count 1, and received data
`0xa5`.

The complete command vocabulary is in `dune exec protemu -- sim script -help`. External
`pad VALUE` and `occupied MASK` are deliberately simulator-specific; they are not portable
device operations or a claim about future physical wiring.

## Completion and handoff

P3.4 is complete for the in-process integrated simulator backend. P3.5 now supplies the
fixed recoverable hardware loader, authoritative wire encodings, timing envelope, and
validated response replay/commit contract in
[`p3.5-hardware-loader.md`](p3.5-hardware-loader.md).

P3.6 must implement a physical transport backend and run it against wrapper simulation,
load and run two images without regenerating RTL, and state whether board verification
occurred. It must add queue transport for data exchange; report step, pin configuration,
and trace as unsupported until hardware exists; reconcile compact wire STATUS with the full
portable record; define transport failure for infallible-looking status functions; map
simulator cycle budgets to physical time; and settle richer wire-refusal mapping. Simulator
pad injection and simulator-side trace are optional backend capabilities, not requirements
that a physical device falsely advertise. Parent P3 remains open until the P3.6 backend,
two-image reload, recovery, and observed transaction evidence satisfy its exit gate.
