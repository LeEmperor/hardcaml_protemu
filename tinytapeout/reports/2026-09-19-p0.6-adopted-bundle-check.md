# P0.6 adopted-bundle check, 2026-09-19

Question: is the `hardcaml_asic` declaration in `bin/asic_bundle.ml` the single
authority for this project's ASIC build inputs — does it emit repeatably, does
the emitted RTL still pass the wrapper behaviour the hand-written path passed,
and does the library actually refuse a second authority?

This is a bundle and declaration record, not a physical run. It is the evidence
for P0.6 here and for ASIC P5.2 in the library
([`phase_plan.md`](../../../hardcaml_asic/docs/phase_plan.md)). The physical
evidence is the separate P0.5b record.

The flop count cross-checks: the P0.5b physical run reported 13 flops and 94
mapped standard cells for this design, so generic synthesis and the hardened
netlist agree on sequential state, and technology mapping roughly doubles the
combinational cell count. That is the only area-like number available here; it
is not a die-area or utilization result.

Conclusion: the declaration is the authority. Emission is repeatable, the
generated metadata/configuration/SDC match what was declared, the emitted RTL
still passes the wrapper trace the hand-written path passed, and the library
rejects a conflicting clock, source list or target-derived setting with a
diagnostic that names the key. `tinytapeout/info.yaml` and
`tinytapeout/src/config.json` are no longer inputs to this path; they survive
only for the legacy `check-p0.sh` / `stage-project.sh` staging path, and
retiring that path is a separate decision.

Limitations: nothing here is physical evidence — no hardening, no timing, no
DRC, no board. Synthesis is generic, not mapped to the CMOS5L standard-cell
library, so the cell counts above bound nothing about area or congestion; at
0.25% utilization in the P0.5b run, this design has not tested either. Memory is
untouched, and P0.7 is where area, congestion and routability first get
exercised.

An earlier run of this same check, at `88a6600d190a3561047242d3cea41a75ccd3935f`
with `dune-project` and `hardcaml_protemu.opam` dirty, also passed all four
checks, at identity
`c6d137dece4bbef3c31ef9ad664b323a07baef53c23d4dca743023ab48176243`. All four
generated files were byte-identical to this run's. That is worth recording as a
property rather than a footnote: **the bundle identity moves when git state or a
declared input's content moves, even when nothing the flow reads changes.**
`dune-project` and `hardcaml_protemu.opam` are declared inputs, so ordinary
library-surface commits move it. ASIC P5.4 needs a physical run taken from a
clean-tree bundle; this emission and the `b699c816…` one at `7e29ecd` are
clean-tree data points, but neither has yet been hardened.
